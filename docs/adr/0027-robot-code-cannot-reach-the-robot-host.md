# 0027. Robot code can't reach the robot host: classic 1.11.2's class checks, and the agent's hooks out of reach

- Status: Proposed
- Date: 2026-11-05

## Context

Classic Robocode 1.11.2 (2026-10-31, GHSA-h2ch-39mm-r68h) fixed a sandbox that wasn't enforced on Java 24+, where the SecurityManager is gone: robots could run commands, use the network and read and write any file. Its fix checks robot classes as they load, on every Java version (`RobotClassLoader`, `RobotClassRewriter`, `RobotClassVerifier`):

- an allowlist of Java packages and classes with a denylist of dangerous members (sockets, processes, `ClassLoader`s, `java.lang.invoke`, `Proxy`, `Unsafe`, virtual threads, ...); a class that breaks it is refused and the robot punished;
- rewritten calls that check their arguments: file output only in the robot's data folder, file reads only in its package and data folders, `File.delete`/`mkdir`/`exists`/`list` the same, deserialization only of the robot's own, Robocode's and common Java classes (`robocode.util.Robot*`), reflection only on the robot's own classes or on members the robot could use directly, no `setAccessible` on others (`RobotReflection`), `getResourceAsStream` only inside the class path, and `Math.random()` from Robocode's generator (`RobotMath`);
- robot class loaders give robots only Java, Kotlin and `robocode.*` classes from the parent, not the libraries Robocode uses;
- at most 5 threads besides the robot's run thread, checked every turn (`RobotThreadManager.checkThreadCount`), the extra ones interrupted.

All of it but the thread count and one file check is behind `RobocodeProperties.isSecurityOn()`. The file check: `ThreadManager.createRobotFileStream`, which opens a robot's `RobocodeFileOutputStream`, refuses a file that isn't directly in the robot's data folder and punishes the robot. robocode-s's robot host runs classic's robot side with `NOSECURITY=true` (design §8), so moving to the 1.11.2 jars (done 2026-11-05) brings the thread count, the file check and the bug fixes, nothing else. The file check is held back for now (item 2, *Robots' files*). Also not behind it: robot classes are always defined through `loadRobotClassLocally` (a `findClass` of its own), the classes a robot's main class refers to are all loaded before it starts, and `findResource`'s fallback (Java 9's bug 389 work-round) refuses names with `..`, `\` or `:`.

robocode-s confines robots differently (ADR 0019): one robot per JVM, in an OS sandbox (seccomp and Landlock on Linux, an AppContainer on Windows, Docker), talking over stdio. That covers what 1.11.2 protects the host machine from, network, processes, files outside the robot's grants, wherever the sandbox has a filesystem layer, and the rumble requires one that does. It doesn't cover:

1. **Local battles without a filesystem sandbox:** macOS (no OS sandbox; the default is `none`), Linux without Landlock, and `--sandbox none`. There a downloaded robot has the user's files, as with classic's `NOSECURITY`.
2. **What a robot can reach inside its own JVM.** The robot host, the determinism agent and classic's robot side share the JVM with the robot, and nothing stops robot code from using them:
   - **The work counter (deterministic mode).** The agent gives each robot's classes a counter, `long[] {limit, count - limit}` (`RobotRandomness.fuel`), through `System.getProperties()` under `robocodes.determinism.fuel`, and keeps it in a static field `robocodes$fuel` of every robot class. Robot calls to `System.getProperties()` go to `RobotSystem`, which leaves the agent's keys out, but the agent tells its own calls from robot code's by what follows them (`ldc "robocodes."`, `WorkMeter.systemCalls`), and a robot whose source says `System.getProperties().get("robocodes.determinism.fuel")` compiles to exactly that. Reflection on its own class (`getDeclaredField("robocodes$fuel")`) or a class compiled against a stub with that field reach it too. A robot that winds its count back is never late, however much it computes, and since it does so deterministically, verification re-runs (ADR 0023) reproduce it: nothing would notice.
   - **The rest of the agent and the host:** under `NOSECURITY` the robot class loader hands robot code any class of the JVM's class path, so `Class.forName` and reflection reach `RobotRandomness` (random streams, the virtual clock, the scheduler of ADR 0025), `RemotePeer` (the protocol: the server still checks every command, as classic's engine does, but a robot could misreport its work or its threads) and classic's engine classes.
3. **Threads:** classic always allowed 5 (the SecurityManager until 1.11.1, the turn check since); robocode-s allowed any number. Virtual threads run outside the robot's thread group and outside ADR 0025's scheduler (they are reported, not run deterministically).

The owner's goals (2026-11-05): ship the 1.11.2 jars, mirror its checks, and if possible without a new deterministic rules version, so that results recorded with today's rules stay valid.

## Decision (proposed)

**1. The agent's hooks are out of robot code's reach** (deterministic mode).
- The agent finds robot code's own `System` calls (`getProperties`, `getProperty`, `getenv`, `lineSeparator`) in the class as it was loaded, before it adds any code of its own, and sends every one of them to `RobotSystem`, whatever follows it. Its own lookups are then the only ones left.
- Robot classes may not name an agent member: the agent refuses a class that refers to a field or method whose name starts with `robocodes$` (before it adds its own). Not by throwing from its `ClassFileTransformer`: the JVM ignores that and defines the class uninstrumented, unmetered. The agent instead replaces each such instruction with a `throw new SecurityException(...)` and reports the robot through the host (`punishSecurityViolation`, as classic's refusals).
- Reflection that uses a `robocodes$` member (`Field.get`/`set`, `Method.invoke`, `setAccessible` on one) throws as a member the robot may not use. Finding them (`getDeclaredFields`) stays as it is, so a robot that lists its own fields sees what it saw before.
- Calls to the methods the agent replaces (`System.getProperties`, `nanoTime`, `currentTimeMillis`, `Math.random`, the `Thread` methods of ADR 0025, `identityHashCode`, ...) by reflection go to the same replacements as direct calls (`RobotReflection`, below, is where they pass).

**2. Robot classes are checked as they load: classic 1.11.2's checks, turned on.**
- The robot host runs classic with security on (`NOSECURITY=false`). On Java 21 without `-Djava.security.manager=allow`, `System.setSecurityManager` throws `UnsupportedOperationException`, which classic catches (`HostManager.initSecurity`): no SecurityManager, and robot classes verified and rewritten as they load, as on Java 24+. *To check first:* that `RobocodeSecurityPolicy`'s `Policy.setPolicy` is harmless without a SecurityManager, what else `isSecurityOn()` changes (`RobotThreadManager.waitForStop` forces a stop on threads that don't end at a round's end; `getPermissions`; the robot class loader's parent delegation, which must still find the robot host's `robocode.*` replacements), and that classic's `--describe` runs (listings) refuse the same robots as battles.
- So: the same checks in classic and deterministic mode, with and without the agent, under every sandbox, and the files of local robots limited where no OS sandbox limits them (macOS, Linux without Landlock).
- The parent allowlist keeps robot code from the agent (`io.github.nhofsted.robocodes.*`), the host, protobuf, ASM and classic's engine. The agent's own classes that robot classes call after instrumentation (`RobotSystem`, the hooks behind `System.getProperties()`) are reached by the instrumented code, not by name from the robot's class file, which is what the verifier checks: the verifier sees the class before the agent does (classic rewrites and verifies in `defineClass`'s caller; the agent's `ClassFileTransformer` runs inside it).
- **The agent adapts to the rewriting so that counted work and randomness don't change:** it sees the rewritten class, so it treats each `robocode.util.Robot*` replacement exactly as the call it replaced: `RobotMath.random()` draws from the robot's `Math.random` stream (ADR 0009) at `Math.random`'s price; `RobotFileInputStream`, `RobotFileReader`, `RobotObjectInputStream`, `RobotFileAccess.*` and `RobotReflection.*` cost what the JDK calls they stand for cost (ADR 0026), and their own code isn't counted.

- **Robots' files, the same on every platform.** Classic checks robot file paths with the platform's own separator, and some robots build theirs with Windows's: cf.RiO.RiOx 4.2.1 and hadur2.Hadur 3.12 (and HadurTeam 3.11) write `getDataDirectory() + "\\" + name`, in the data folder on Windows and beside it, in the parent folder, on Linux and macOS (3 of the 1,375 corpus jars use getDataDirectory with a lone `"\\"`). Classic 1.11.2's file check (above, outside its security switch) therefore disables them on Linux and macOS but not on Windows: rumble volunteers on different platforms would get different results for the same battle. Until this is decided, the robot host keeps 1.11.1's `createRobotFileStream` (`ClassicFileWrites`, a subclass of classic's `ThreadManager` put in classic's container before anything uses it): robots write as they did, held to their home by the sandbox and to classic's quota. The decision to take with item 2: treat `\` as a separator in robot file paths on every platform (as on Windows, where these robots were written and where classic's checks then let them write in their data folder), applied to reads as well as writes, so that the checks can come back without disabling them.

**3. The corpus decides what is let through.** Before release, every robot of the rumble's lists (1v1, melee, team; the 1,375 jars of the difftest corpus as a first pass) is loaded by the 1.11.2 host with security on, and the refused ones listed with the reason. Classic's own check of 388 RoboRumble robots refused 5 (commit d1c64c6). For each refused robot one of:
- the robot uses something harmless that 1.11.2's lists miss: robocode-s allows it (a short list of our own, documented with the robot and the member) and offers the fix upstream;
- the robot really does something classic 1.11.2 now refuses: robocode-s refuses it as classic does. Classic 1.11.2 refuses it on every Java version, so it no longer runs in classic RoboRumble clients that update either.

**4. Threads as classic: at most 5, no virtual threads.**
- The 1.11.2 jars bring classic's turn check (`checkThreadCount`, not behind `isSecurityOn`), shipped with them on 2026-11-05: a robot with more than 5 live threads besides its run thread is punished (its energy drained and the robot disabled, classic's `punishSecurityViolation`, once per battle) and its extra threads interrupted. The check counts the robot's thread group, where ADR 0025's scheduler keeps all of a robot's threads; in deterministic mode a thread's end is a point the scheduler decides, so the count is the same in every run. Classic up to 1.11.1 punished the same robots, when they started the sixth thread (the SecurityManager's `checkAccess(ThreadGroup)`).
- *Fixed with it (2026-11-05):* the robot host didn't survive a punishment from classic's robot side in the middle of a turn. `RemotePeer.punishBadBehavior` sent the disabling `Execute` and marked the round finished, but the robot's code went on calling `execute`, took the round's `ROUND_OVER` from the inbox there and then waited for it again in `waitForBattleEndImpl`, while the main thread waited for the robot's thread: a hang until the server's hard limit (60 s of real time), so battles of such robots differed from run to run. Now a punished robot's next `execute` throws `DeathException`, as in classic (its peer is killed), and the wait for the round's end remembers a `ROUND_OVER` already taken. The same path serves item 2's refusals. `crates/runner/tests/threads.rs` (`a_robot_with_too_many_threads_is_punished_reproducibly`, ignored: needs Java) fights `testbots.Pool`, which keeps a pool of 2 threads per round and has 6 in round 3, twice: no hard limit, the same outcome.
- Virtual threads are refused by the class check (item 2), as in classic. ADR 0025's report of them stays for robots refused that way (none should reach a battle).

**Rules version.** No new deterministic rules version if the checks change the battles of no robot in the rumble's lists. That is verified, not assumed:
- seeded deterministic battles of every corpus robot with the 1.11.1 host (security off) and the 1.11.2 host (security on) give byte-identical recordings, with the refused robots of item 3 set apart;
- the live difftest replays every recorded classic battle identically, and recorded production rumble tracks re-run byte for byte (`rumble` client's `Runner`);
- the threaded robots of ADR 0024/0025 (Toad, Fermat, TNT, Rapture, FlamingForest and `robots/testbots`) give the same recordings with the thread limit as without.

If a robot in the lists changes anyway (refused, or punished for threads), the choice is the owner's: allow it (item 3's list) and keep the rules, or bump the rules version (the runner refuses a host with other rules, and the server's verification only compares battles of the same rules).

## Consequences

- One robot sandbox inside the JVM, classic's own, kept in step with classic by taking its jars: what classic refuses, robocode-s refuses, in every mode and on every platform; the OS sandbox stays the outer wall.
- The work counter, clock, random streams and scheduler can't be reached by robot code, so deterministic results and verification can be trusted against robots that try.
- Robots that classic 1.11.2 refuses are refused here too (unless item 3 allows them), with classic's message in the robot's output.
- The agent depends on classic's rewriting: a classic release that rewrites more calls needs the agent to price them as the originals, or results change. Moving to a new classic version is a deliberate step with the same checks as this one.
- Startup cost: classic verifies and rewrites each robot class once, with ASM, before the agent instruments it.

## Measured (2026-11-05)

Rumble battle hashes (`crates/rumble-client/examples/battle-hashes.rs`, the hash verification compares; seeded, deterministic, 10 rounds each), the 1.11.1 robot host against the 1.11.2 one:

- **Threaded robots** (TNT, Fermat, Toad, Rapture, FlamingForest against sample.Crazy, and a 7-robot melee of them): identical, with the 1.11.2 jars alone and with the shipped host.
- **final-5** (30 corpus duels, 6 melees): with the 1.11.2 jars alone, 34 identical; the two melees with cf.RiO.RiOx (31, 34) differ, from its punished file writes (they reproduce on 1.11.1: three runs, one hash). With the shipped host (`ClassicFileWrites` and the punishment fix): all 36 identical.
- **batch-13** (60 corpus duels): all identical, with the 1.11.2 jars alone and with the shipped host.
- **testbots.Pool** (a pool of 2 threads a round, never shut down): punished in round 3 for its sixth thread; with the jars alone the robot host then hung until the hard limit and three runs gave three outcomes; with the fix, the same outcome every run (`a_robot_with_too_many_threads_is_punished_reproducibly`).
- **Live difftest** of final-5's and the samples' classic 1.11.1 recordings (49): the shipped host gives the 1.11.1 host's verdicts, turn for turn: 44 `OK`, and the same 5 `FAIL`s at the same turns (21-duel, 30, 33, 34 and 35-melee: recordings older than rules 3, ADR 0026).

Still to run before item 3: the rest of the corpus.

Not covered by this change: the difftest oracle (classic's own battle side) runs 1.11.2 with its file check, so new classic recordings of robots like RiOx disable them; they need the oracle to keep 1.11.1's file writes as well.
