# 0025. Deterministic threads for robots: one virtual CPU per robot

- Status: Accepted (the owner's decisions of 2026-10-31, below)
- Date: 2026-10-27, decided 2026-10-31

## Context

Deterministic mode counts each robot's work (ADR 0014) and decides skipped turns by it (ADR 0018), but threads that robot code starts run on the OS scheduler, and `Thread.sleep` and timeouts use real time (ADR 0014, "Not covered"). Robots with threads are therefore not reproducible: the same seeded battle ends differently from run to run and from machine to machine, and rumble verification penalized volunteers for it. ADR 0023 flags such robots and makes their verification no-fault; ADR 0024 has the agent detect robot-started threads and report them (`Execute.threads`). This ADR makes them reproducible. The robot's work counter is shared by its threads and updated without synchronization, so concurrent threads even lose counts.

Verified on 2026-10-27:
- **ak.Fermat 2.0:** `DataWriter extends Thread`, started in `onDeath`, writes `<opponent>.txt`; later rounds read it back. A seeded melee (seed 5001203142733927833, ten robots) gave two different outcomes in 6 runs, first diverging in round 27.
- **TNT.TNT 0.99.1, rapture.Rapture 2.13, techdude.forest.FlamingForest 1.1:** a `PatternAnalyzer` thread loops on `Thread.sleep(500)` and switches the gun's pattern.
- **florent.test.Toad 0.14t:** a tree thread that polls a buffer forever, lowering its priority to 1 when the buffer is empty; rebuild and restore threads; the main thread busy-waits on their flags (`while (addingInProcess) {}`).

A scan of the 1375 RoboRumble jars (ASM, robot classes only, bundled Kotlin left out) finds 8 that start threads from robot code: the five above, dam.MogBot 2.9 and jasolo.Sonda 0.55 (threads that save and load data files) and inonit.robocode.javascript.MyFirstRobot 1.1 (Rhino; its threads are in Rhino's debugger and shell). None uses `java.util.Timer`, executors or `java.util.concurrent` locks; only the Rhino robot has `synchronized`, `wait` and `notify` next to threads. The corpus difftest excludes TNT, Rapture and Toad as not reproducible in classic.

Classic: a robot's threads run in its thread group, concurrently with its main thread (on a multi-core machine, in parallel); classic times only the main thread. At a round's end `RobotThreadManager.waitForStop` interrupts each of them every 100 ms for up to 3 s of wall time; with security on (as in the rumble) it then stops them with `Thread.stop`, which threw `ThreadDeath` in them up to Java 19 and does nothing on Java 20 and later, where such threads run on into the next rounds.

## Decision

In deterministic mode, the determinism agent gives each robot **one virtual CPU**: the robot's threads run one at a time, and the CPU changes hands only at points that depend on what the robot executes (`RobotThreads`, `ThreadCalls`).

- **Which threads:** a thread the robot's code starts on one of the robot's threads, directly or through the JDK's thread-starting facilities (the innermost caller of `Thread.start()` or `start(ThreadContainer)` outside `java.lang.Thread`, `java.util.Timer`, `java.util.concurrent`, the agent and Kotlin's helpers is a robot class): its own threads, its `Timer`'s, its executors'. The thread that starts the first one, the robot's main thread (classic's `runThread`), joins too. Threads the JDK starts for itself on a robot's thread (Java2D's disposer when a robot paints) are left alone, as are threads robot code starts on a thread outside the scheduler. Robots without threads of their own never get a scheduler.
- **How:** the agent patches `java.lang.Thread` (one patch, shared with ADR 0024's report): `start()` and `start(ThreadContainer)` register the new thread before it exists; `run()`, the `run()` of robot classes that extend `Thread` and of library classes that do (`TimerThread`, `ForkJoinWorkerThread`, Kotlin's `thread {}`) wait for the CPU before the thread's code runs; `exit()` hands the CPU on; `sleep(long)`, `sleep(long, int)`, `join(long)` (which `join()` and `join(long, int)` call) and `interrupt()` go to the scheduler on the robot's scheduled threads. It also patches `Object.wait(long)` (which `wait()` and `wait(long, int)` call) and `LockSupport`'s `park`, `parkNanos`, `parkUntil` and `unpark`, so JDK code that blocks for the robot (a `Timer`'s queue, every `java.util.concurrent` lock, condition, latch and queue) goes through the scheduler too; and in `java.util.Timer` and `java.util.concurrent` it rewrites `System.nanoTime()` and `currentTimeMillis()` to the robot's virtual clock in classic's time (so their timed waits fit, `Time` below) and tells the scheduler before every `notify()` and `notifyAll()`. These hooks act only on the robot's scheduled threads, and only when the blocking call comes from the robot's side (its own code, or the JDK's for it; not the robot host's or classic's waits for the next turn on the main thread). On any other thread they return at once, so the JDK's behaviour and even its stack traces stay the same (a first version rewrote robot code's `sleep` calls instead, and the helper frame showed in the stack trace that mn.nano.SkippedTurns prints when `sleep` throws, which changed its recording). In robot code, the native `Thread.yield` is rewritten to a synthetic helper, and monitors and notifies call `RobotSync` (below).
- **Switch points:** a thread blocks (`sleep`, `join`, a monitor another of the robot's threads holds, `Object.wait`, `LockSupport.park`) or ends; `yield`; the end of a **quantum**; the end of the main thread's turn. A new thread waits in line; the starting thread goes on.
- **Quantum:** 100 µs of virtual time, 625 000 counted instructions. The count is already checked where robot code can repeat (loop starts and handlers, ADR 0018); that check now first does `if (fuel[1] >= 0) robocodes$limit(fuel)`, which asks the scheduler only once the count reached the limit (inline, reusing the block's stack-map frame; a block that starts with `new` calls the helper unconditionally). The limit is the lowest of the robot's work cutoff (ADR 0018), the running thread's quantum end and the end of a slice (below). Busy-waiting on another thread therefore ends, at the same instruction everywhere. Robot code's monitors and notifies call `RobotSync`, a public class of the agent that robot classes link to directly (their loader delegates to the agent's), with one volatile read as long as no robot of the JVM has threads. Below the limit the call does nothing; at the cutoff the check after it throws, as before.
- **Next thread:** the first waiting thread of the highest Java priority, round-robin among equals. Classic caps a robot's thread group at its main thread's priority (`NORM_PRIORITY - 1`), so helpers can never outrank the main thread, only yield to it: Toad's idle tree thread (priority 1) then only runs when the main thread waits.
- **The main thread's turn:** while it runs, the robot's other threads of its priority get their quanta in turn. Their work counts toward the turn, as decided in ADR 0018.
- **The turn's end:** where classic's robot side executes (`BasicRobotProxy.executeImpl`, before the robot's commands go out; the same code in classic and in robocode-s), the other threads that wait for the CPU run until none can, or for at most what is left of the turn's budget less a quantum, and at most 1 ms (`TURN_NANOS`, the virtual clock's time between turns for waiting on the other robots, ADR 0014). This work counts toward the turn too, but it can't by itself make the main thread late (but for running past the slice's end to the next check). A round's first turn gives none: the work before the first execute is free and isn't measured.
- **Time:** all of the robot's threads, its `Timer` and `java.util.concurrent` read one clock, the robot's virtual clock (ADR 0014): turns, counted work and the time it slept. A turn adds `TURN_NANOS` (1 ms) as before, and `CLASSIC_TURN_NANOS` (8 ms) once the robot started a thread of its own (from then on, to the battle's end), so that a sleep of d lasts about d / 8 ms turns, as in classic. `CLASSIC_TURN_NANOS` is classic's wall time per turn in the threaded robots' battles on the calibration machine of ADR 0014, measured on 2026-10-31 with the classic oracle (tools/difftest; main's agent, so their threads ran freely and slept in real time; quiet machine): TNT, Rapture and FlamingForest against lancel.Lynx 1.09 took 7.2–9.5 ms per turn (median 8.3); the Fermat melee 1.3 ms, but Fermat doesn't sleep. `PatternAnalyzer`'s `sleep(500)` thus wakes about every 62 turns. `sleep`, timed joins, waits and parks end when the clock reaches their deadline: a sleeper wakes at the first switch point after it, earliest deadline first. When nothing of the robot can run, the clock moves on to the earliest deadline (the main thread's, if it waits), so a robot that times its own sleep with `nanoTime` or `currentTimeMillis` sees what it asked for (or a little more).
- **Sleeping on the main thread:** in classic the battle doesn't wait for a robot whose main thread sleeps (or waits with a timeout): it is late and skips the turns that pass meanwhile. In deterministic mode the time its main thread sleeps, or the clock moves while it waits with nothing else to run, makes its turn late by d × `TURN_BUDGET_NANOS` / `CLASSIC_TURN_NANOS` of counted work (ADR 0018): about one turn per 8 ms, with classic's limits (more than 30 skipped turns disable it, 240 for I/O robots). The robot host adds it to the turn's work (`cpu_nanos`); the classic oracle's patched `RobotPeer` reads the same. A robot without threads that sleeps on its main thread takes no real time: the clock moves on and the call returns, with no scheduler; with an invalid argument or when interrupted the call goes on to the JDK, which throws as before, with the same stack trace. Helpers' sleeps and timed waits don't make the main thread late; neither does their work at the turn's end (above).
- **Reported threads (ADR 0024):** the robot host reports (`Execute.threads`) only what the scheduler doesn't run deterministically: threads robot code starts on a thread outside the scheduler, and robots whose classes use virtual threads (`Thread.ofVirtual`, `startVirtualThread`, `Executors.newVirtualThreadPerTaskExecutor`) or `Unsafe`'s `park`/`unpark` (checked as each class loads; reported at once, or at the robot's next turn when classic loaded the class on another thread). Robots whose threads are all scheduled are not reported, so the rumble can verify their battles.
- **Monitors:** robot code's `monitorenter` first calls `RobotSync.enter(o)` and its `monitorexit` then `RobotSync.exit(o)`; a `synchronized` method is rewritten in place to the same explicit monitor (entered first, left before every return and in a handler for everything that rethrows, as javac compiles a `synchronized` block), so stack traces stay the same. The scheduler keeps each monitor's owner and count: entering one another of the robot's threads holds puts the thread in line for it (first come, first served) and hands the CPU on, so a thread only takes the real monitor when the scheduler gave it, and a thread preempted inside a `synchronized` block never makes another block in the JVM. An exception unwinding through the block leaves it through javac's handler (or the method's added one); a thread that ends while it holds monitors gives them up.
- **`wait` and `notify`:** a scheduled thread's `o.wait(timeout)` gives up the monitor (all its entries) and the CPU and waits in `o`'s queue; `notify` takes the first in the queue, `notifyAll` all of them, in that order; a timed wait ends at its deadline on the virtual clock (in classic's turns, as `sleep`), an interrupt ends it too. Then the waiter waits for the monitor and the CPU, and throws `InterruptedException` if it was interrupted, as in the JVM. Meanwhile it sits in a real `o.wait()`, so the JVM releases and restores the real monitor; the thread that hands it the CPU wakes it there (and a real `notify` that wakes it earlier doesn't let it go on). `LockSupport.park` parks in the scheduler with its permit, `unpark` from one of the robot's threads makes it ready.
- **Interrupts:** robot code's `interrupt()` sets the flag as usual; a sleeping, joining, waiting or parked target gets in line (a waiter first for its monitor) and throws `InterruptedException`, or returns from parking, when it runs.
- **The round's end:** classic's `RobotThreadManager.waitForStop` first awaits the main thread (as before), then the scheduler, driven from the battle side: the other threads are interrupted 30 times (as classic does every 100 ms for 3 s), each time running until they all wait, for at most 1 ms of counted work; then they are stopped as classic did up to Java 19: a `ThreadDeath` where each next runs, with its limit at its count, so its loops throw too. A thread that still doesn't end never runs again. Classic's own wait (3 s of wall time per thread, with re-interrupts) is skipped for such robots. The next round starts without threads; the work cutoff applies to all of this.
- **Not covered:** virtual threads and `Unsafe`'s parking (reported, above); JDK code that blocks while it holds the CPU outside these hooks (native I/O, a monitor of JDK code held by another of the robot's threads when JDK code calls back into robot code that gets preempted, the lock of a class another of the robot's threads is initializing): such a thread blocks for real while it holds the CPU and the robot hangs until the server's hard limit; a monitor the main thread entered before it started its first thread (the scheduler doesn't know it is held); a wait on an object that JDK code outside `Timer` and `java.util.concurrent` notifies (a thread's `join` of a thread outside the scheduler waits for real). No corpus robot does any of these.
- **The robot's environment (2026-10-31):** robots must not see the volunteer's environment, for determinism and because reading environment variables from a sandbox leaks information. Both modes, every path (no sandbox, `os` with seccomp and Landlock or Windows' AppContainer, `bwrap`, docker and podman):
  - **The process environment** of a robot JVM is cleared and fixed: `PATH=/usr/bin:/bin`, `LANG=C.UTF-8`, `TZ=UTC` and `HOME`, the robot's own folder (bwrap adds `PWD`, the same folder; older bwraps can't unset it). On Windows the system's folders (`SystemRoot`, `windir`, `SystemDrive`, `PROCESSOR_ARCHITECTURE`, `LOCALAPPDATA`) and the sandbox's own `PATH`, `TEMP` and `TMP`. A container gets the pinned image's (`PATH`, `JAVA_HOME`, `JAVA_VERSION`, `LANG`, `LANGUAGE`, `LC_ALL`, its entrypoint's `JRE_CACERTS_PATH`, `PWD` and `SHLVL`), `HOME`, `TZ=UTC` and the host name `robocode-s` instead of the container's id. Without a sandbox the runner used to pass the user's whole environment, tokens and keys included; now none of it reaches a robot (`AWS_*`, `GITHUB_*`, `ROBOCODES_*`: the rumble's and an agent's tokens). The one exception is a robot the runner's library starts over TCP (possible only without a sandbox; the runner's own battles use pipes): it gets its battle's robot token, which it needs to connect, and it can read all of the user's files anyway. Classic mode gets this too: it is a security property.
  - **JVM flags** (both modes, and the classic oracle): `-Duser.language=en -Duser.country=US` (the oracle's and the calibration machine's), `-Duser.timezone=UTC`, `-Dfile.encoding=UTF-8`, `-Dstdout.encoding=UTF-8`, `-Dstderr.encoding=UTF-8` and `-Duser.name=robocode-s`. Deterministic mode adds `-XX:ActiveProcessorCount=1` (one CPU per robot: `availableProcessors()`, the common pool and the GC no longer follow the machine), `-Xms` equal to `-Xmx` (so `totalMemory()` and `freeMemory()` start the same everywhere; they still depend on garbage collection) and `-Dline.separator=\n`.
  - **Robot code, deterministic mode:** the agent rewrites robot classes' calls to `System.getenv(name)` (`null`), `System.getenv()` (an empty map), `getProperty`, `getProperties` (a copy without the agent's hooks) and `lineSeparator()` (`\n`) to `RobotSystem`, after counting, so they cost what they did. Neutral values: `user.name` robocode-s, `user.home` and `user.dir` /home/robot, `os.name` Linux, `os.version` 0, `os.arch` amd64, `java.home` /opt/java, `java.class.path`, `java.library.path`, `sun.boot.library.path` and `jdk.module.path` empty, `line.separator` `\n` (Windows' `\r\n` changed what robots write and read back). `file.separator` and `path.separator` stay the platform's: robots build paths with them. Classic mode doesn't run the agent and keeps the real properties: its robots read the fixed environment above.
  - **Who reads them** (a scan of the 1 375 corpus jars' bytecode, 2026-10-31): `System.getenv` no robot; `getProperty` 12 robots: `line.separator` voidious.Diamond 1.8.28; `java.version` eem.EvBotNG v12.8 and three catcat20 robots (Lambda, Matcha, shape.Theta); their own keys (unset, so their defaults) zen.Mirage 0.9.5, pc.Wavelet 1.5, dev.kurtw.KurtBot 0.2, lxx.Emerald 0.6.5, jd.Nullstride 2.3.3, morbid.MorbidPriest 1.0 and the JavaScript host of inonit.robocode.javascript.MyFirstRobot 1.1; `Runtime.freeMemory`/`totalMemory` florent.XSeries.X2 0.17 and axeBots.SilverSurfer 2.53.33fix; `Calendar`/`TimeZone` 10 robots (the catcat20 three, axeBots Musashi, Okami and SilverSurfer, ustimaw.NightmareTeam, shinh.Entangled, Diamond, aaa.r.ScalarR), mostly for file names and timing; `java.text` formats, `Scanner` or `Locale` 82, `String.format`/`printf` 71. Diamond, catcat20.Lambda, axeBots.SilverSurfer and florent.XSeries.X2 against Lynx give recordings byte-identical to main's on this machine (en_US, UTC): the change only shows on machines with another locale or time zone, where `String.format("%.3f", x)` gave `1234,568` (nl_BE), which `Double.parseDouble` rejects; with the flags it gives `1234.568` there too.

## Alternatives

- **Run the other threads only at the turn's end, to quiescence, without preemption.** No quantum and no check helper, but a busy-waiting main thread (Toad's `while (addingInProcess) {}`) waits until its work cutoff and crashes, and a thread that never waits (Toad's tree thread) runs until the cutoff each turn. Busy-waiting needs preemption at counted points, so the quantum stays; a quiescence-only gap would also give helpers unlimited work outside the budget.
- **Free helper work: the other threads use the time the robot waits for the others, uncounted** (after its `Execute` is sent, in `RemotePeer` and in classic's `RobotPeer`). Closest to classic on a multi-core machine, where helpers don't slow the main thread. It needs a hook in each peer and the gap's work subtracted from the counted work on both sides, and ADR 0018 decided that helper work counts. Not chosen (decision 1).
- **Plain round-robin, ignoring priorities** (Linux JVMs ignore them by default). Toad's idle tree thread would then take every other quantum of the main thread's turn, which would likely make it skip turns (not measured); with priorities it uses only the gap (`-Drobocodes.threadPriorities=false` switches them off, to compare).
- **No threads in deterministic mode** (`start()` throws, or runs the thread's code synchronously). Simple, but TNT's analyzer loops forever and would hang its robot, and the eight robots lose their behaviour.
- **A per-thread work counter** (count the main thread only): rejected in ADR 0018 for its cost.
- **Let unfinished threads run on into the next round**, as classic on Java 20 and later. Accumulates threads (TNT starts one per round) and makes the next round depend on leftovers; stopping them matches the rumble's classic clients up to Java 19.

## Classic compatibility

Each classic run interleaves threads differently, so no single deterministic order is "right"; the choices above aim at classic's typical behaviour. What deterministic mode loses against classic on a multi-core machine:
- Helper work counts toward the robot's turn (ADR 0018); in classic it runs in parallel and only the main thread is timed. Helpers get at most 1 ms per turn outside the main thread's quanta.
- `sleep` lasts a fixed number of turns (d / 8 ms); in classic it depends on how fast the battle runs: against cheaper opponents, in melee, classic turns are faster and a sleep spans more of them (the Fermat melee ran 1.3 ms per turn). The same holds for a main thread's sleep: classic skips as many turns as pass meanwhile. testbots.Sleeper (80 ms every 60 turns, against sample.Crazy, seed 11) skipped 13 038 and 13 104 turns in two runs of plain classic (real timing, main's agent): while it slept, a turn took about 5 ms there, Crazy being cheap. robocode-s skips about 6 100 (the oracle with this agent 6 020) and scores 278 against classic's 323 and 350. mn.nano.SkippedTurns (sleeps that make it skip until it is disabled, every round) skipped 2 230 and 2 234 turns in classic, 2 215 here (the oracle with this agent), and sample.Fire scored 2 200 and 2 204 in classic, 2 192 here (2 100 before, when its sleeps took no turns). Counting a sleep as work (late by d itself, not d / 8 ms × budget) gave Sleeper 23 300 skipped turns: too many.
- Unfinished threads are stopped at the round's end, as by classic up to Java 19, not left running as on Java 20 and later.
- Robot code's `Thread.stop()` throws `UnsupportedOperationException` on Java 21, in both.

- **Versions:** `DETERMINISTIC_RULES` (server, and the rumble backend's copy in `rumble-core`) and `rulesVersion()` are 2, so a robot host without the scheduler is refused and a robot host with it isn't used with an older server. `ENGINE_VERSION` stays 1, and with it the rankings: battles of robots without threads of their own are byte-identical (above), and those of the robots with threads were never reproducible and are no-fault in the rumble (ADR 0023), so no verification compares a result of the old rules with one of the new. Design §4.4 notes the exception; the test that pins the two versions together now pins (1, 2).
- **Rollout:** the rumble backend reports its rules (`GET info`) and clients refuse other rules, so the release with rules 2 and the backend with rules 2 go out together. The five robots flagged nondeterministic on prod (`nd`: Toad, Fermat, TNT, Rapture, FlamingForest) may be unflagged only after the rumble's `minClient` is the release carrying this change: an older client still runs them nondeterministically (and reports their threads).

## Decisions (the owner, 2026-10-31)

1. **Helper work counts** toward the turn, in the main thread's turn and at the turn's end (ADR 0018), as proposed.
2. **At a turn's end** helpers run for at most the turn's spare budget less a quantum, and at most 1 ms.
3. **Priorities** are honoured.
4. **Quantum:** 100 µs of virtual time.
5. **The round's end:** unfinished threads are stopped (as classic up to Java 19).
6. **Versions:** only `DETERMINISTIC_RULES` / `rulesVersion()` are bumped (to 2); `ENGINE_VERSION` and the rankings stay (Consequences).
7. **Monitors, `wait`/`notify`, `java.util.concurrent`, executors and `Timer`** (asked on 2026-10-31): covered, in the same rules version 2 (above); only virtual threads and `Unsafe`'s parking are reported.
8. **The report:** only what the scheduler doesn't cover is reported, so scheduled robots become verifiable; the five flagged robots are unflagged once `minClient` carries this (Rollout).
9. **The time scale of `sleep`:** calibrated against classic's wall time per turn (`CLASSIC_TURN_NANOS`, 8 ms), part of rules 2.
10. **Sleeping on the main thread** (asked on 2026-10-31): costs turns as in classic, about d / 8 ms (ADR 0018's late turns, classic's limits); the clock moves through sleeps, one clock for all of a robot's threads; helpers' sleeps cost the main thread nothing. Rules 2.
11. **The robot's environment** (asked on 2026-10-31): a fixed process environment on every path, in both modes; fixed locale, time zone, encodings and user name, and in deterministic mode one processor, a fixed heap, `\n` lines, no environment and neutral properties for robot code. Proposed here: classic mode keeps the real system properties (only the environment and the flags are fixed there), `file.separator` stays the platform's.
12. **The pinned Java** (asked on 2026-10-31): `rumble run` refuses a `--java` or `$ROBOCODES_JAVA` that isn't the pinned Temurin release (its `release` file: `IMPLEMENTOR="Eclipse Adoptium"`, `IMPLEMENTOR_VERSION` of `jre::RELEASE`); without one it downloads the pinned JRE, and containers use the pinned image. `robocode-s battle` takes any Java.
13. **The hard limit** (asked on 2026-10-31): a robot disabled by it is reported per robot (`BattleOutcome.hard_limits`, `RobotResult.hardLimit`, `hardLimit` in `--json`), and such battles are no fault in the rumble (ADR 0023) without flagging the bot: the limit is the machine's, and a flag would exempt every later battle of the bot from checks.
